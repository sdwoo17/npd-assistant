# PDF 개선 요구사항에 따른 리서치 작업 재구성

2026-09-15. 기존 서비스 분석, FGI, VoC, 선진사례의 네 문서에서 도출한 46개 수용 항목을 기준으로 화면과 서버 작업을 연결했다. 원본 PDF·화면 캡처·실제 고객 자료는 저장소에 포함하지 않는다.

## 작업 흐름

1. **기존서비스분석**에서 PRD·매뉴얼 등 프로젝트 문서를 선택한다. AI는 제품 이름부터 서비스 요약·상세·기능·사용 시나리오·지표·제약·향후 희망사항까지 14개 필드를 채운다. 자료에 없는 내용은 빈칸과 확인 질문으로 남긴다.
2. 오른쪽 인터뷰는 추출 문서, 현재 필드, 앞선 대화를 입력으로 받는다. 필드 변경안을 먼저 보여 주고 PO가 고른 항목만 반영한다. `FUTURE_REQUEST`를 현재 기능 필드에 넣으려는 응답은 거부한다.
3. 보고서를 저장하면 필드·출처·질문·인터뷰를 버전별로 보존한다. **Edit**는 저장 당시 문맥으로 편집본을 열며, 다음 저장은 같은 보고서의 새 버전이 된다. 별도 분석은 별도 보고서로 남는다.
4. **페르소나**에서는 고객 조사 보고서·서베이·심층 인터뷰와 profile 프롬프트로 후보를 만든다. 서로 다른 집단의 후보를 비교하고 선택한 후보만 풀에 등록한다. PRD·PRFAQ를 고객 근거로 제안하지 않는다.
5. **FGI**에서 공유 페르소나 풀, 설계, 가이드, 세션, 검토 디브리프를 보존한다. 완료 후에는 원본을 수정하지 않는 후속 분석 대화를 연다. 디브리프는 버튼을 눌렀을 때 생성하며 동일 입력은 재사용한다. 다른 초안을 요청할 때에는 재생성 사유를 기록한다.
6. **VoC**는 선택 작업이다. 실제 리뷰·상담 로그를 확보한 후 실제 분석을 수행한다. 합성 자료 분류는 별도 시연 선택이 필요하며, 페르소나 발언을 실제 VoC 결과로 저장할 수 없다. 기존에 잘못 분류해 저장한 가상 VoC도 근거·PRD 입력에서 제외한다.
7. **저장된 리서치 결과 / PRD 작성**에서 본문과 자료 성격을 확인하고 정확한 버전을 체크한다. 새 PRD에는 선택한 결과만 전달한다. 결과나 선택이 바뀌면 기존 초안도 재검토해야 한다. 최종 PRD 확정은 같은 결과를 포함하는 연구 묶음의 기존 준비 조건을 통과해야 한다.

상단에는 현재 프로젝트·단계와 저장 버튼이 고정된다. 분석 초안 저장과 검토본 저장은 구분하며, 공통 검색에는 검토한 결과만 들어간다. 저장된 결과는 프로젝트 내에서 접근 가능한 지식이고, 다른 프로젝트에는 노출하지 않는다.

## 서버 계약과 호환성

- `/api/service-contexts`와 `/extract`, `/save`, `/interview`, `/apply`, `/complete`, `/edit`: 서버가 프로젝트와 역할을 결정하고 매 변경에 현재 버전과 트랜잭션 epoch를 검사한다.
- `/api/research-inputs`: 검토된 `research_result` 또는 `debrief`의 종류·ID·버전을 저장한다. 다른 프로젝트, 오래된 버전, 미검토 자료를 거부한다. `/api/definitions/link-research`는 최종 검토에 사용할 연구 묶음과 선택 결과가 일치하는지 확인한다.
- `/api/persona-candidates/generate`, `/adopt`: 문서에서 후보 1~6개를 제안하고 선택한 후보를 한 트랜잭션으로 등록한다. 실제 고객이 아닌 합성 프로필이다. 이름 중복·풀 상한·원본 철회 검사를 유지한다.
- **기존 `/api/personas/generate` 응답은 활성 persona에서 초안 batch로 변경됐다.** 이전 클라이언트는 반환된 `batch_id`, `expected_version`, `indices`로 `/api/persona-candidates/adopt`를 호출해야 한다. 실제 응답의 batch ID 키는 `id`다. 채팅 생성도 `persona_draft_created` 상태와 `persona_batch_id`를 반환한다. 직접 작성·선택 등록 API는 유지한다.
- `/api/studies/followup`: 완료한 연구의 설계·가이드·기존 발언·디브리프를 별도 대화에 연결한다. 기존 완료 세션의 변경 금지는 유지한다.
- `/api/studies/demo`: 저장된 합성 시연을 명시적으로 가져온다. 모델 장애의 대체 응답이 아니며 실제 고객 데이터나 현재 제품 기능의 증거가 아니다.
- `/api/debriefs`: 같은 입력에 대한 저장 결과를 재사용한다. `regenerate: true`에는 `reason`이 필요하다.
- `/api/voc/classify`: 기본은 실제 VoC다. `synthetic_mode: true`는 합성 분류 시연용이다. 합성 여부를 실제 관측으로 바꾸지 않는다.

## 외부 리뷰 설정

- Android: 서버 `ANDROID_PUBLISHER_TOKEN`에 관리 앱 접근 토큰을 공급한다. [Google Play Reviews API](https://developers.google.com/android-publisher/api-ref/rest/v3/reviews/list)의 고정 주소·페이지 토큰을 사용한다. 임의 앱 전체 리뷰 스크레이핑을 보장하지 않는다.
- iOS: 기존 App Store 공개 리뷰 RSS를 사용한다. 관리 앱의 App Store Connect API는 기존 서버 API에서 유지한다.
- S3: 서버 `NPD_REVIEW_S3_BUCKET`, 선택적 `NPD_REVIEW_S3_PREFIX`(기본 `reviews`)와 AWS SDK 인증을 설정한다. 현재 프로젝트의 `reviews/<project_id>/*.csv`만 읽으며 CSV는 3MB 이하이다. 원본 CSV의 실제/합성 표시를 보존한다. [S3 GetObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/object/get.html)를 사용한다.

토큰·AWS 인증·실제 파일은 커밋하지 않는다. 실제 Google/iOS/S3 권한·네트워크 범위와 Bedrock 문서 요약 품질은 실환경에서 확인해야 한다.

## 검증 경계

`tests/test_research_flow.py`는 원본 철회, 프로젝트 격리, 미래 요청의 현재 기능 변경 차단, 보고서 이력, PRD 선택 범위, 페르소나 선택, 완료 FGI 후속 분석, 실제/합성 VoC, 리뷰 수집 계약을 검사한다. `tests/browser_flow.cjs`와 `tests/ui_flow.cjs`는 실제 HTTP/SQLite와 합성 모델로 사용자 흐름을 검사한다. CI는 새 스크립트 문법 검사와 전체 회귀 검사를 포함한다.

저장소의 지원 검증 기준은 Linux/WSL2의 Python 3.12이다. Windows 네이티브 전체 검사에는 기존 디렉터리 초기화·심볼릭 링크·POSIX 파일 권한 관련 실패가 있다. 이 구현은 실제 모델의 문서 충실도, 실제 고객 UAT, 별도 CloudFront 앱의 화면 변경·배포 완료를 증명하지 않는다. 특히 복수 페르소나 집단의 타당성과 근거의 의미적 정확성은 실제 모델·자료로 PO가 검토해야 한다.
